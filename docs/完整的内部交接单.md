# 完整的内部交接单

用户把开发任务交给 Claude Code，开发 bot 完成以后，要请 Codex 独立审查。程序会为整项协作创建一个 taskId，假设它是 T123。

开发 bot 准备第一次交接时，还会生成一个只服务于本次投递的 dispatchId。图里把它简写成 D001，实际代码生成的是一段 12 位十六进制字符串，例如 `a2748bd45e14`。

| 字段         | 当前值       | 用途                               |
| ------------ | ------------ | ---------------------------------- |
| taskId       | T123         | 把后续审查和返工归到同一项协作任务 |
| round        | 1            | 表示这是 bot 之间的第一次交接      |
| dispatchId   | D001         | 标识当前这一次投递                 |
| toBotId      | reviewer     | 限定只有审查 bot 可以领取          |
| workspaceDir | 示例项目目录 | 让审查 bot 进入同一个项目          |
| prompt       | 审查要求     | 告诉 Codex 接下来要做什么          |

这张交接单会先通过 `register()` 写进所有 bot 共享的 CollaborationInbox。这一版的多台 bot 由同一个进程启动，所以它们拿到的是同一份收件箱实例。随后，开发 bot 在原话题里新发一条富文本消息，真正 @ 审查 bot。飞书消息只需要带上 D001，相当于把一个取件码送到对方手里。

审查 bot 收到飞书事件后，会确认这条消息真的提及了自己，再用 `任务编号：([a-f0-9]{12})` 从文本中提取真实的 dispatchId。接着调用 `consume('a2748bd45e14', 'reviewer')`，从共享收件箱里领取完整交接单。领取成功后，这条记录立即删除，同一条通知不会被重复执行。

Codex 完成审查以后，最终回答会成为开发 bot 的下一项任务。程序继续沿用 taskId=T123，把 round 加到 2，并为这次反向投递生成新的 dispatchId=D002。开发 bot 收到 D002 后，用同样的方式领回审查意见，继续修改同一个项目。

| 交接                  | taskId | round | dispatchId |
| --------------------- | ------ | ----- | ---------- |
| 开发 bot 交给审查 bot | T123   | 1     | D001       |
| 审查 bot 交回开发 bot | T123   | 2     | D002       |

用户最开始把需求交给开发 bot，不算协作轮次。这里数的是 bot 之间真正发生了多少次交接。taskId 贯穿整项协作，round 记录当前走到哪一轮，dispatchId 则让接收方准确领取当前这一次投递。

这套机制的核心很简单：飞书负责把取件码送到目标 bot，CollaborationInbox 负责保存真正要执行的任务。接下来写代码时，你看到的每个字段和分支，都可以放回这次往返里理解。
